Why index?

Without an index, every query scans every row. With an index, the DB jumps to the right location in 3–4 page reads regardless of table size.

No index — seq scan
SELECT * FROM employees
WHERE salary = 80000;

→ Read ALL 1,000,000 rows
→ Compare each one
→ ~8,000 page reads
→ Slow
With index — O(log n)
SELECT * FROM employees
WHERE salary = 80000;

→ Traverse B-Tree (3 reads)
→ ctid → heap page (1 read)
→ Row found
→ Fast

What is a page?

8KB block — minimum unit of disk I/O. The OS never reads less than one block. Heap pages store rows; index pages store B-Tree nodes. Same structure, different content.

Key insight: Page structure is identical — same header, same slot array, same 8KB. Only content differs. Buffer pool treats both as plain 8KB blocks.

Slot & offset

Slot = a two-number directory entry inside a page. Offset = byte position of a row within that 8KB block. Nothing more.

slot 1:  offset = 7500,  length = 80
          ↓
          "go to byte 7500 inside this page, read 80 bytes → your row"

Full lookup chain

ctid=(page 4, slot 3)
→
load page 4 (8KB)
→
slot 3: off=7340
→
jump to byte 7340
→
row found

Full page always loads (I/O min unit = 1 block). But Postgres does not scan the page — it jumps directly using the offset. No per-byte scan inside the page.

Why indirection? — the slot is stable, the offset can change

Without slots

Index stores offset directly. Row moves after UPDATE/VACUUM → every index entry must be updated. O(n) index rewrites per row move.

With slots

Index stores slot number (stable forever). Slot stores offset (can change freely). Row moves → only one slot entry updates. Index untouched.

Page split

When a full page gets a new key, Postgres can't extend it — the 8KB block is fixed. It splits the page into two halves and promotes the middle key to the parent.

Buffer pool

Fixed RAM cache. Every page — heap or index — goes through it. Disk I/O only on a miss. Nothing more complex than that.

shared_buffers = 256MB   ← postgresql.conf

HIT  →  page in RAM     →  nanoseconds
MISS →  load from disk  →  milliseconds (1000× slower)

Buffer pool is cold — all pages on disk.

LRU eviction — when pool is full

New page needed, pool full:
  → find LRU page (least recently used)
  → if dirty (modified) → write to disk first
  → evict it → load new page

Root page almost never evicted — every query touches it.
Heap pages more likely evicted — accessed less frequently.

Cardinality & selectivity

Cardinality = distinct values in a column. Selectivity = rows matched / total rows.

Low selectivity value → few rows match → index useful. High selectivity → many rows match → planner skips index.

Composite index

An index on multiple columns. The key in each leaf node is a tuple — all columns combined, sorted lexicographically by the column order you declare.

CREATE INDEX idx_dept_salary ON employees(department, salary);

Leaf key = (department, salary) combined:
  ("Eng", 42000) → (page 1, slot 3)
  ("Eng", 67000) → (page 2, slot 1)
  ("Eng", 80000) → (page 4, slot 2)
  ("HR",  55000) → (page 3, slot 1)
  ("HR",  95000) → (page 5, slot 2)
  ("Mkt", 72000) → (page 6, slot 4)

Sorted: dept first, salary second within each dept.

Column order — the most important rule

The index is sorted by the first column first. Second column is only sorted within each value of the first. This determines which queries can use the index.

Left-prefix rule — visualized

Leading column used — index works
WHERE dept = 'Eng'
  → tree can navigate to dept='Eng' block
  → scan only those entries
  → index used ✓

WHERE dept = 'Eng' AND salary = 80000
  → navigate to dept='Eng', salary=80000
  → exact match
  → index used ✓

WHERE dept = 'Eng' AND salary > 60000
  → navigate to dept='Eng'
  → scan salary range within that dept
  → index used ✓
No leading column — index skipped
WHERE salary = 80000
  → salary is col 2
  → col 1 (dept) unknown
  → entries are scattered everywhere
  → full index scan or seq scan ✗

WHERE salary > 60000
  → same problem
  → can't anchor on col 1
  → index skipped ✗

→ need separate idx ON (salary)
  for salary-only queries

Covering index — skip the heap fetch entirely

If the index contains all columns the query needs, Postgres never touches the heap. The leaf node has everything.

CREATE INDEX idx_cov ON employees(department, salary) INCLUDE (name);

SELECT name, salary FROM employees WHERE department = 'Eng';
  → index-only scan
  → leaf has: dept + salary + name + ctid
  → query satisfied from leaf alone
  → heap fetch = 0
  → fastest possible read
